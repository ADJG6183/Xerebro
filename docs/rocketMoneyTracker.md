## Logic audit (requested, before continuing) — 3 real bugs found and fixed

- **TransactionDetailScreen.tsx:** clearing the category/note field to empty looked like a savable edit (Save enabled, tapped, screen closed) but silently did nothing — `TransactionAnnotatedPayload` has no "clear this override" sentinel, an omitted key MERGES over the existing annotation rather than clearing it, and `undefined` doesn't survive JSON anyway. Fixed: clearing a field is never treated as a change (`categoryChanged`/`noteChanged` require a non-empty, actually-different value). Clearing a correction back to "no override" isn't supported yet — would need a schema decision (e.g. a tombstone value), not assumed here.
- **httpTransport.test.ts:** the "stalled request times out" test stubbed `fetch` to never resolve, ignoring the `AbortSignal` entirely — a real `fetch` rejects when its signal aborts, but the stub didn't, so the test would have hung instead of proving the timeout. Fixed: the stub now listens for `abort` and rejects, like real fetch does.
- **decisionFlow.test.ts:** the new stalled-pull test hung `getEventsSince` on every call, but `runPurchaseCheck`'s own audit-record write also calls it internally (`sendOrQueue` → `flushOutbox` → `pullOnce`) on a leg this slice does NOT bound (the already-documented "known gap" above). The test would have hung on that unrelated, already-flagged gap instead of testing the initial-pull bound. Fixed: only the first call hangs; later calls behave normally.

None of these were caught by running tests (still can't, in this sandbox) — found by re-tracing the actual control flow by hand. Worth treating this sandbox's inability to execute as a standing reason to keep doing this by-hand trace on anything touching money, auth, or timing, not just at the end.

## External review response (mid-session) — 2 real High-severity bugs confirmed and fixed, plus 5 more findings addressed

Aaron relayed an independent review of the work so far. Evaluated each claim against the actual code before acting, per CLAUDE.md's "evaluate feedback critically" — all 7 were confirmed accurate (not just plausible-sounding), fixed to the extent in scope, with the two bigger UX projects scoped out explicitly rather than rushed:

1. **Response-BODY reads weren't covered by the timeout, only the initial request.** `fetch()`'s promise resolves once headers arrive; the old `fetchWithTimeout` cleared its abort timer right there, before any caller's `res.json()` ran — a stalled body (after a fast TTFB) could hang past the documented cap entirely unbounded. Fixed in `httpTransport.ts`: restructured to a `BoundedResponse { res, aborted, clear }` + `readJson()` pair so the SAME timer/signal spans headers and body — every one of the 10 transport methods updated consistently. New test proves a stalled body times out, isolated from a normal fast request.
2. **Three independently-bounded legs could stack past the documented cap.** Pull (≤3s) → refresh (≤3s) → re-pull (≤3s) could reach ~9s total against a documented 4s refresh-race cap — same root issue as the "budget-math gap" flagged earlier in this tracker, now actually fixed instead of just flagged. Fixed in `decisionFlow.ts`: one deadline computed once, `remainingMs()` shrinks for each subsequent leg instead of a fresh window per leg. `raceRefresh` now takes an explicit timeout parameter instead of reading `deps.refreshTimeoutMs` itself.
3. **The purchase check waited on the audit record's network upload before returning the answer**, even though the record was already durable locally by then. Fixed: `runPurchaseCheck` now awaits only `outbox.enqueue(...)` (local, fast) and fires `flushOutbox(...)` detached (not awaited) — matches the spec's own words ("remote audit upload can happen later") literally. `recordStatus` is now always `"queued"` at return time by construction (accurate — the upload was never checked) rather than occasionally `"synced"` by having waited for it. Updated `AskScreen.tsx`'s wording, which used to presume offline-ness whenever `"queued"`; it now uses the real `offline` signal (from the pull/refresh legs) to decide tone, since "queued" is normal now, not a warning.
4. **A faster, newer purchase check could be overwritten by an older, slower check's late-arriving AI explanation.** `checking` resets to `false` the instant the verdict renders (beat 1), re-enabling the amount input while the explanation (beat 2) can still be in flight — a user could edit and re-check before the first check's explanation arrives, and that stale explanation would land on top of the new answer. Confirmed by hand-trace (this codebase has no component-test infrastructure to automate it — flagged honestly rather than faked). Fixed in `App.tsx`: a `checkRequestId` ref gates every `setAnswer`/`setEnhanced` call against "is this still the current request"; editing the amount or description while an answer is showing now explicitly invalidates it (bumps the request id, clears the stale card) instead of leaving a verdict on screen for an amount the user has since changed.
5. **"Can't verify right now" didn't distinguish "stale, refresh might help" from "reconciliation was never established, no refresh fixes that."** The data already existed (`VerificationResult.boundedBy`/`reason`, confidence.ts) but the template explanation never branched on it. Fixed in `explanation/template.ts`: the specific "not established yet" sentinel reason now gets its own honest phrasing ("refreshing or reconnecting won't change that by itself"); every other CANT_VERIFY reason (freshness, drift-after-reconciliation-was-attempted, data quality) keeps the existing phrasing, which is still correct for those. Does NOT build the reconciliation evidence path itself — that's still the stage-1 decision #4 research spike, deliberately out of scope this increment.
6. **An overdue bill silently stopped reducing available cash the moment its due date passed.** Confirmed in BOTH `computeFinancialState` (the real decision math) and `planModel.ts`'s separate, duplicate `sumDueWithin` (display only) — `Bill` has no paid/settled status yet (that's stage 4, separate work), so treating an elapsed date as payment was simply wrong, not a simplification. Fixed `computeUpcomingObligationsMinor` (financialState.ts) to drop the `nextDue >= todayLocal` lower bound — an overdue bill now counts indefinitely until actually settled or edited. Deleted `planModel.ts`'s duplicate `sumDueWithin`/`addDays`; it now calls the engine function directly, so Budget's displayed total can never diverge from what a purchase check actually used. New tests in `state.test.ts` and `planModel.test.ts`.
7. **Chat has no way to disclose unsynced device edits**, even though Home already shows them optimistically — `ChatScreen` received no pending-count information at all. Fixed: added a `pendingCount` prop (App.tsx already tracks this) and a banner shown whenever it's nonzero, disclosing that answers may not reflect those changes yet. Does not yet identify *which* data an individual answer's scope covers — that would need the server tool-call response to carry scope metadata, left as a smaller, separate follow-up.

**Scoped out, not fixed, with a specific reason each (not silently dropped):**
- **Connection recovery actions** (per-state retry/reconnect buttons, auto-refresh while importing) — real gap, but wiring an actual retry flow per connection state plus foreground polling is new feature surface, not a bug fix; needs its own slice.
- **A dedicated, resumable history-review flow** ("N transactions need review" entry point separate from the account list) — same reasoning: a real UX improvement for heavy users, but new screen/navigation work, not a fix to what exists.

## Scope choices made explicit, not silently dropped

- Spending's filter UI wires up direction (all/income/expense), category (tap a breakdown row), and search. The view-model also supports an account filter and a pending/posted filter — no dedicated control for either yet; trivial to add once prioritized, not blocked on anything.
- Category breakdown shows the top 6 as tappable chips (layout choice); the full breakdown is still computed and available, and every transaction's category is still visible in the list regardless.
- Merchant-rename correction (engine supports it via the same `TransactionAnnotated` overlay) has no UI yet — spec's Spending section only asked for category/note.
- Clearing a category/note correction back to "no override" isn't supported — the event schema has no clear-sentinel; would need a small schema decision if wanted.
